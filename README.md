# Mooki

电商售后客服的 Agent。听懂用户在问什么 → 查订单、物流、政策 → 判断这件事能不能办 → 给方案，办不了就转人工。

[![Python](https://img.shields.io/badge/python-3.12-blue)](https://www.python.org/)

一句话：**用一个受控拓扑替代 ReAct，把"模型可能乱来"的地方从流程里挤出去**；重点不在能不能答，

## 为什么做成"受控"Agent

售后是个挺拧巴的场景。问题高度收敛——用户翻来覆去就问那十来件事；但答错的代价很高，退款金额说错、时效承诺错，都是要赔钱的。

这种场景我不太敢让模型自己决定下一步。ReAct 那种"思考—调用—观察"的循环看着聪明，但它的不确定性恰好落在最不能出错的地方：可能多调一次工具，可能自己编一个金额，也可能在犹豫的时候给用户一个模糊承诺。

所以流程是写死的：

```
load_context → intent → plan → act → observe → respond
                  │       │      │       │
                  ↓       ↓      ↓       ↓
               澄清追问  白名单  熔断   转人工 / 降级
```

模型只有两处自由度：判断用户想干什么（10 类意图 + 4 档紧急度），以及决定调哪个工具、填什么参数。工具从白名单里挑，循环最多 3 轮，P0 级（投诉、12315、资损）直接跳过所有判断送人工。

这条路的代价是灵活性，收益是可预测：任何一个动作都能在 trace 里复现，不需要猜模型当时在想什么。

## 跑起来

```bash
pip install -r requirements.txt
make index      # 建知识库索引（含向量化）
make test       # 92 个单测
make smoke      # 6 条典型链路，看输出
make serve      # http://127.0.0.1:8000
make eval       # 全部离线评测（检索/意图/端到端/多轮/规模）
make concurrency # 幂等并发压测（同一笔退款 16 并发撞进来）
```

也可以直接容器起：

```bash
docker compose up --build      # app + redis，账本落卷
```

打开 `127.0.0.1:8000` 就能聊，右边是实时 trace：每次意图投票的明细、调了哪个工具、检索改写成了什么、上下文用了多少 token，都能点开看原始 JSON。

默认离线模式——LLM 和 embedding 都走本地确定性实现，所以跑测试和评测不需要任何 key。想接真模型，`cp .env.example .env` 填四个字段就够了，业务代码一行不用改：

```bash
MOOKI_LLM_OFFLINE=false
MOOKI_LLM_BASE_URL=https://api.deepseek.com/v1
MOOKI_LLM_API_KEY=sk-xxx
MOOKI_LLM_MODEL=deepseek-chat
```

同一条问题「SO20261018006 我不想要了，能退款吗」在两种模式下的差别：

| 模式 | 回复 | 耗时 |
|---|---|---|
| 离线 | 已为你核实：退款判断：可退，可退金额 139.0 元，阻断项 无，签收至今 3 天，退款单号 RFB9F9E398F0，当前状态 refund_pending | ~15ms |
| 在线（DeepSeek-chat） | 可以退。您的订单 SO20261018006（便携榨汁杯 400ml，实付 139.0 元）签收至今 3 天，在 7 天无理由期内，可退金额 139.0 元，无阻断项，退款单号 RFB9F9E398F0，当前状态为退款处理中。已签收订单需走退货退款流程，请填写退货物流单号，商家验收通过后发起退款。 | 6.0s，7 次 LLM 调用 |

离线那版是拼接模板，能跑通链路但没法看。**消融和对比强制走离线**，否则模型每次输出都不一样；要看真模型下的观感、延迟、成本，单独跑 `make eval-online`。

## 几个设计上的取舍

### 意图为什么要投三次票

单靠 LLM 判意图，遇到"取消订单以后钱退哪去了"这种话会摇摆：订单和退款都沾边，换个说法答案就变了。所以让三路各投一票——LLM、向量近邻、业务关键词——再按权重融合。

三路的量纲完全不一样（类别+置信度 / 余弦相似度 / 命中强度），没法直接平均，投票是唯一能把它们统一起来的形式。冲突太大的时候不硬判，输出 `need_clarify` 让上层追问一句。

权重这里我踩过坑。一开始按"LLM 最强"拍了 0.55，也就是给它最大话语权。后来做留出实验发现，在样本少的情况下 LLM 那一路反而最弱，融合后的准确率 0.35，**比最强的单路 0.85 还低**。改成按 dev 集标定的 `rule 0.65 / llm 0.25 / dense 0.10` 之后才追平。

所以现在配置里那三个权重是量出来的，不是拍的。

### 检索：改写比排序重要

链路是 `改写 → BM25 ∥ 向量 → RRF → 时效过滤 → 去重 → 重排`。

做消融之前我以为重排是最值钱的一环，结果打脸：加改写 R@3 从 0.85 涨到 0.925，加重排 R@5 一点没动，只把 MRR 提了 0.036。

想想也合理。用户说的是"钱怎么还没回来"，知识库里写的是"退款到账时效"，两句话字面几乎不重叠，召回阶段就漏了，重排再准也救不回来。重排解决的是"召回来的几条里谁排第一"，不是"有没有召回来"。

另外一个反直觉的现象：RRF 融合单独用，R@5 是 0.875，比纯 BM25 的 0.900 还低。因为两路质量不等价，等权融合等于用弱的一路稀释强的一路。这也是我后来给权重留了参数的原因。

### 订单号不能靠摘要记

多轮对话里最怕的不是记不住，是"记住了但记错了"。

一开始我用滚动摘要压缩历史，40 轮之后 token 是省了，但订单号 SO20261018006 被摘要抹掉了——后面所有查单工具全部失效，用户得重新说一遍单号。

现在订单号、金额、诉求这些抽成结构化槽位单独存，**不参与压缩**，摘要只压叙述性内容。40 轮会话 token 压掉 79%，订单号保留率 100%。

还踩过一个更蠢的：早期版本在 `append` 里直接 `ltrim` 截断窗口，超出的历史既不进摘要也不留槽位，等于凭空消失。现在折叠只在 `maybe_compress` 里做，因为只有那里拿得到 LLM。

### 退款要能回滚

退款是跨系统操作：平台单改了状态，支付网关那边可能失败。如果本地先改成"退款中"、网关没收到，这笔账就悬空了。

所以订单状态不用 UPDATE，用 append-only 账本：每次只追加一条事实，当前状态由重放推出来。三个东西保证不重复扣钱：

- **状态机**：`paid/shipped/delivered → refund_pending → refunded`，非法转移直接拒
- **幂等键**：重复请求返回第一次的结果，不重新执行
- **补偿**：网关失败时追加一条 `refund.cancel` 把状态回滚

补偿这里也有个坑。回滚要回到"进入退款流程之前"的状态，我一开始取的是上一跳状态，结果 `refund.cancel` 的上一跳就是 `refund_pending`，回滚完还停在退款中，等于没回滚。现在单独记一个 `origin_status`。

### 幂等键的唯一性不能靠进程内的锁

写完账本我以为幂等做完了，压测一跑就露馅：**16 个并发请求，退了 16 次**。

原因是那把 `threading.Lock` 挂在 `OrderLedger` 实例上。每个请求各建一个 `ServiceTools`（多 worker 部署就是这样），锁就退化成各管各的，谁都看不见对方写过的幂等键。不是并发压力不够，是互斥放错了层。

改成 SQLite 的 `idem_key UNIQUE` + `BEGIN IMMEDIATE`，把唯一性交给存储层，进程内锁只作为减少冲突的优化：

| 账本后端 | 并发方式 | 成功创建 | 命中幂等 | 退款单号数 |
|---|---|---|---|---|
| SQLite | 16 线程 | 1 | 15 | 1 |
| SQLite | 16 进程 | 1 | 15 | 1 |
| jsonl | 16 线程 | 16 | 0 | 16 |
| jsonl | 16 进程 | 9–16（每次不同） | 其余 | 同左 |

`make concurrency` 可复现。jsonl 后端保留着，因为评测要看可读的事实文件；线上默认走 `data/ledger.db`。

### 转人工不是"建完工单就结束"

之前 P0 投诉的处置是：建单 → 回一句"2 小时内联系你" → 结束。用户说的那句话、系统查到的事实，全留在这一条 trace 里，接手的专员看不见，用户还得从头再说一遍。

现在转人工是**挂起**：节点用 LangGraph 的 `interrupt` 把 run 停在检查点上，把工单号、紧急度、诉求摘要一起交出去；专员处理完调 `POST /api/handoff/resume`，答复送回同一个 `thread_id`，run 继续走完并落记忆。

```
用户: 我要投诉，再不解决就去12315
  → handoff 节点建单 TK71820BDFD1 → interrupt（run 挂起，进程可以重启）
专员: 调 resume 送回答复
  → run 从检查点恢复 → reply = 专员的答复 → persist
```

这是**唯一一个非 LangGraph 不可的地方**：挂起意味着状态得存在进程之外、下次还能找回来。`mini_graph` 没有检查点，进程一重启上下文就没了，这件事它做不到。所以默认仍然关着（`MOOKI_ENABLE_HUMAN_INTERRUPT=true` 才开）——人工不在线时把用户挂住，比直接建单更糟；没开时退回原来的"建单即返回"。

踩到的坑：检查点里存的是我们自己的 Pydantic 类型（`IntentResult`/`Urgency`…），默认序列化器会告警说未来版本要拒绝，得显式给 `JsonPlusSerializer` 放行这几个模块。

### trace 里不该出现手机号

trace 会被存进内存、推到前端、导出做客诉复盘。用户随口一句"我电话 138xxxx，你们打这个"，原样进 trace 就等于把个人信息复制到所有下游。

所以脱敏放在 `TraceStore.emit` 这**唯一一个写入口**，手机号、身份证、银行卡、邮箱都打码保留首尾（`138****5678`）。只在各自的出口做迟早会漏——后来加个导出接口、加个报表，就绕过去了。

订单号不动：它是排查必须的定位信息，不是个人信息。地址也没做正则，中文地址没有稳定模式，硬匹配会把"XX 路 3 号"这类正常描述一起打掉，宁可在采集侧就不收整段地址。

另外 `/api/stats` 现在除了 token 还报 `est_cost_cny`（单价按 `MOOKI_PRICE_*` 配，没配就报 0，不拿拍脑袋的数字当账单）和端到端 p50/p95，延迟和成本能一起看。

## 评测

八组实验，`make all` 能全部复现，报告落在 `eval_out/`。

**先说一件不好看的事：换掉评测集之后，指标全线下跌。**

上一版是 39 条知识、40 条 query，检索 R@5 到过 0.950、意图同源准确率 0.950。把语料扩到 134 条、检索 query 扩到 137 条、意图扩到 105 条之后：

| 指标 | 旧集 | 新集 |
|---|---|---|
| 检索 Recall@5（全链路） | 0.950 | 0.861 |
| 检索 Recall@1（全链路） | 0.775 | 0.547 |
| 意图同源准确率 | 0.950 | 0.791 |
| 端到端平均分（1-5） | 4.08 | 3.25 |

跌的原因不是代码变差，是旧集本身有问题：query 是照着知识库的小节标题写的，意图 query 是照着 exemplar 写的，而两条通道直接在 exemplar 上建库——**那 0.950 是泄漏出来的，不是能力**。新加的 65 条意图 query 完全脱离 exemplar，分数就回到真实水平。这件事上一版 README 里只写了"分数偏高，只看机制"，现在有了对照，才算说清楚。

**检索消融**（137 条标注 query，top_k=5）

| 配置 | R@1 | R@3 | R@5 | MRR |
|---|---|---|---|---|
| 纯向量 | 0.460 | 0.686 | 0.759 | 0.572 |
| BM25 | 0.504 | 0.774 | 0.832 | 0.629 |
| +RRF | 0.482 | 0.781 | 0.839 | 0.619 |
| +改写 | 0.518 | 0.788 | 0.854 | 0.648 |
| +重排 | 0.547 | 0.774 | 0.861 | 0.663 |
| +域先验 | 0.540 | 0.759 | 0.861 | 0.654 |

架构整体带来 R@5 +0.102、R@1 +0.087。三条结论都还在，只是幅度缩水：

- **改写仍然是最值钱的一环**（+0.015 R@5，MRR +0.029）。用户说"钱怎么还没回来"，文档写"退款到账时效"，字面几乎不重叠，召回阶段就漏了，重排再准也救不回来。
- **RRF 单独用仍然不如纯 BM25**（0.839 vs 0.832 持平，R@1 反而低）。两路质量不等价，等权融合就是用弱的一路稀释强的一路。
- **重排只动排序不动召回**：+重排后 R@5 不动、MRR 继续涨。这符合它的作用域。

**按词汇重叠度分桶，架构的增益全在难样本上**

| 重叠度 | n | 纯向量 R@5 | 全链路 R@5 | 增益 |
|---|---|---|---|---|
| 低（0-0.17） | 45 | 0.422 | 0.622 | **+0.200** |
| 中（0.18-0.30） | 45 | 0.867 | 1.000 | +0.133 |
| 高（0.30-0.91） | 47 | 0.979 | 0.957 | -0.021 |

只看总体 R@5 会同时高估系统能力（被容易样本拉高）和低估架构价值（难样本上的增益被平均掉）。语料扩了，这个结构性结论没变，反而更稳了。

dev/test 漂移从 0.154 降到 0.038 —— 这是扩容最直接的收益：40 条时漂移比配置间差异还大，那时的结论不可用；137 条时漂移已经小于最小增益。

**意图**

同源评测 0.791（Macro-F1 0.799，弃权率 12.4%）。可信的仍然是留出实验：

| 通道 | dev | test |
|---|---|---|
| 规则 | 0.800 | 0.850 |
| 向量 | 0.200 | 0.350 |
| 朴素贝叶斯 | 0.267 | 0.300 |
| 融合（未标定权重） | 0.367 | 0.350 |
| 融合（dev 标定权重） | 0.800 | 0.850 |

权重是按 dev 集量出来的 `rule 0.65 / llm 0.25 / dense 0.10`，不是拍的。一开始按「LLM 最强」给了 0.55 的话语权，融合后反而比最强单路还低——这说明调权重必须用手上的数据，不能靠直觉。

**但这组权重只在离线替身上成立**：换成真模型后再标定一次，最优回到 `llm 0.55 / rule 0.40`，沿用离线那组反而掉 9 个点。详见下文「意图权重重标定」——这也是整份报告里唯一一条被自己的后续实验推翻的结论。

注意每折留出后每类只剩 4 条训练样本，这里能说明的只有"小样本下规则更稳"，不能反过来推"向量没用"。

**多轮会话**（10 组 / 22 轮，`make eval-multiturn`）

单轮评测看不出跨轮的两类错，所以单独做了一组：每轮必须有答复、槽位在后续轮次仍能规划出"需要订单号"的工具、写操作整段会话只出现一次。

- 会话通过率 60%，槽位保留率 75%，**写操作重放 0 次**
- 失败集中在关键词：追问句短、指代多，检索会漂到相邻条款上（"过期的券能补吗" 命中"优惠券使用规则"而不是"券过期与补发"）

"写操作重放 0 次"是这次专门修的：以前用户追问"那钱多久到账"，意图仍是 refund，规划层会照链路再跑一遍 `refund.apply`。账本幂等键能保证不重复扣钱，但工具白跑一次、答复退化成复读上一条结论，用户是能感知的。现在规划层读账本状态，已落账就降级成检索，trace 里留一条 `plan_skip`。

**并发**（16 并发，`make concurrency`）

见上文"幂等键的唯一性不能靠进程内的锁"。SQLite 后端 1 创建 + 15 幂等，jsonl 后端 16 个退款单号。

**记忆和延迟**：40 轮会话 token 压缩 79%、订单号保留 100%；端到端 P50 6ms / P95 10ms，最大单项是 `persist` 节点。

**规模敏感性**：注入近重复变体从 134 涨到 439 条，全链路相对纯向量的优势在 +0.015 到 +0.029 之间波动，排序侧（NDCG）比覆盖侧衰减更早——干扰主要影响"该排第一的有没有排第一"，而不是"有没有进前五"。

**向量后端**：LSA 与哈希在不同规模上互有胜负。这一项只有接真实 embedding 服务才有意义，`make embedder` 已经把三后端对比写好了，但目前 **API 后端没实跑过**，见"已知问题"。

**在线模式**（`make eval-online`，DeepSeek-chat，n=24）

| 指标 | 数值 |
|---|---|
| 平均分 / 通过率 | **4.417 / 87.5%**（离线 3.25 / 45.8%） |
| 关键词命中率 | 87.5% |
| 延迟 | P50 **3824 ms** / P95 **6114 ms** |
| 单轮成本 | 约 **0.0023 元**（每次约 6 次 LLM 调用、1900 prompt tokens） |

> 这两列**不能直接比大小**：离线判分器是 bigram 覆盖率模板，在线判分器是模型本身，标尺不同。可比的是"同一份题在真模型下的绝对观感"和成本量级。

第一轮跑出来是 4.167 / 83.3%，失败的 4 条里有一条特别值得记：**「发票能不能只开商品不含运费」被判成 logistics**，然后回了一句"你是想查物流轨迹还是改收货地址"。查下去发现不是模型判错，是权重把它压住了——见下一节。按真实通道重标定权重后，这条修好了，整体回到 4.417 / 87.5%。

剩下的 3 条失败集中在两类：

- **d13 / d14 有单据事实但没采信**。工具明确返回"待发货""待付款"，答复却写成"已发货未签收需拦截""仅凭订单号无法判断"。事实与模型先验冲突时模型会选先验——这是受控拓扑也管不住的一段，需要输出后的一致性校验。
- **d24 P0 转人工答得过简**：工单建了、时效说了，但没给赔付来源与到账时间。转人工分支现在是固定话术，没走检索。

**意图权重重标定**（`make eval-intent-online`，n=105）

上面那条 d22 引出一个更根本的问题：三路投票的权重 `rule 0.65 / llm 0.25` 是**在离线替身上标定的**。换成真模型之后，LLM 通道仍然只有四分之一的话语权，模型判对了也会被规则通道压掉。

把 105 条 query 的三路投票用真模型重新取一次，再在 dev 上网格搜索权重（步长 0.05），test 只报一次：

| 权重来源 | LLM | Dense | Rule | dev | test |
|---|---|---|---|---|---|
| 初始假设（LLM 最强） | 0.55 | 0.25 | 0.20 | 0.931 | **0.969** |
| 离线标定（原默认） | 0.25 | 0.10 | 0.65 | 0.890 | 0.875 |
| 在线标定（dev 网格搜索） | 0.55 | 0.00 | 0.45 | 0.931 | **0.969** |

结论是反的：**离线那组权重在真模型下反而更差**（0.875 vs 0.969）。同一份标注数据、同一套融合代码，只因为换了模型，最优权重就从"规则为主"回到"LLM 为主"。

所以权重不是模型的属性，也不是业务的属性，是**「模型 × 通道」这个组合的属性**。现在代码里按 `llm_offline` 自动选一组默认值，显式设了 `MOOKI_INTENT_WEIGHT_*` 才以配置为准。

**在线检索对照**（`make eval-online-retrieval`，n=137）

这条实验是为了回答"短口语问句检索不准，是架构问题还是离线替身的问题"。索引、向量（LSA）、融合参数全不动，只把**改写与重排**换成 DeepSeek：

| 配置 | R@1 | R@5 | MRR | NDCG@5 |
|---|---|---|---|---|
| 离线替身（同义词改写 + bigram 重排） | 0.547 | 0.861 | 0.663 | 0.712 |
| DeepSeek 改写 + 重排 | **0.869** | **0.964** | **0.911** | **0.925** |

137 条里改善 15 条、退化 1 条、其余持平——但 R@1 整整高了 32 个点，说明**排序的上限是被离线替身压住的，不是架构问题**。这也修正了下面"已知问题"里那条关于追问句的判断：短板在替身，真实模型接上去之后同类问句的排序明显好转。

## 踩过的坑

留几个印象深的，都加了测试锁住：

- **SSE 事件发出去前端收不到**。`{"type": "trace_event", **event.model_dump()}`——事件自己也有 `type` 字段，字典展开把外层的覆盖掉了。curl 看服务端一切正常，排查了半天才发现前端一条都没匹配上。
- **LSA 只在知识库上训练，却拿去编码意图样本**。两批文本用词不一样，样本里大量词是 OOV，编码出来接近零向量，向量通道静默退化成"每次都投同一票"。这个 bug 是靠通道消融（`dense_only` 准确率异常）才暴露出来的。
- **评测不幂等**。退款工具改成真的改状态之后，第二次跑评测就命中"已在退款中"，分数每次都变。现在评测和基准都把账本指到临时目录；多轮评测更是必须单独起一个 runtime，否则前面的对话评测已经把这单退过了。
- **离线替身和规则通道同源**。两边都在做关键词匹配，投票就成了重复计票。换成朴素贝叶斯之后假设空间才分开。
- **幂等键的锁挂错了层**。`threading.Lock` 在账本实例上，多 worker 部署时每个请求各持一把，16 并发退了 16 次。见上文并发一节——这类问题看代码是看不出来的，只能压。
- **改写缓存只按 query 做 key**。"那这个能退吗"在不同会话里该改写成不同的查询，只按原句缓存会让后一个会话拿到前一个会话的结果。现在缓存键带上最近两轮历史的指纹。
- **规划阶段的检索没带历史**。应答阶段的 `kb.search` 传了 `history`，工具调用的那一路没传，于是追问句（"三天没更新了怎么办"）检索直接漂到退款条款上。同一个能力两条路径行为不一致，是这类双层架构最容易漏的地方。

## 已知问题

- **没有真实 embedding 服务**。`APIEmbedder` 写好了但没实跑过，报告里的向量通道全是 LSA（共现矩阵做 SVD）。接上 bge-m3 / text-embedding-3 之后要重跑 `make embedder` 才知道值不值。
- **在线结果不可复现**。`eval_out/online_eval.md` 与 `online_retrieval.md` 是 DeepSeek-chat 跑一次的结果，温度不为 0，重跑数字会变；它们的作用是给出绝对观感与成本量级，不是用来给配置排名的。
- **离线替身是词袋模型**，和真实 LLM 的行为差距很大（同一条 query，真实模型意图置信度 0.89，朴素贝叶斯只有 0.3）。离线数字只能做相对比较，不能当线上效果。
- **意图权重只按「在线/离线」二分**。代码现在按 `llm_offline` 二选一，但换到另一个模型（Qwen、GLM）权重未必还合适，正确做法是每换一次模型重跑 `make eval-intent-online` 校一遍。
- **事实一致性没有硬校验**。模型可能不采信工具返回的单据状态（d13/d14），目前靠 prompt 约束，没有输出后校验与重试。
- **134 条语料仍然偏小**。dev/test 漂移已经降到 0.038，结论比 40 条时可靠，但离"能对外说准确率"还差一个量级。
- **人工接管只在单进程内有效**。检查点用的 `MemorySaver` 存进程内存，重启就丢；多副本部署要换 Postgres/Redis 检查点，否则 resume 打到另一个副本会找不到 run。
- **前端是单文件面板**，没有鉴权，也没有多会话列表。
- Docker 镜像在这台机器上没验证过（本地没有 Docker），`docker compose up` 属于"写好了没跑过"。
